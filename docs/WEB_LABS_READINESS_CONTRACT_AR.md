# P1 — عقد معاينة جاهزية مختبر الويب

المسار: `POST /api/v1/web-labs/prepare`، العقد: `aegis.web-labs-readiness.v1`.

هذه المرحلة تقرأ إعدادات موجودة وتوضح النواقص بالعربية. لا تنشئ Asset أو Scan أو LabAttempt أو جلسة Burp، ولا تغيّر تفويضًا أو قبول مزود أو سجل استخدام سر. المصادقة الحالية وسجلات المنصة المعتادة تبقى وفق سلوكها القائم. نتيجة المعاينة ليست تفويضًا، ويعاد فحص الحالة عند التنفيذ لاحقًا.

## مكان الدمج

| المكون | موضعه | ما يعيد استخدامه | خرجه |
|---|---|---|---|
| API | `backend/fastapi_app/routers/web_labs.py` | `get_current_user` وFastAPI الحالي | عقد دخل/خرج مضبوط وأخطاء عربية بلا صدى للمدخل المرفوض |
| خدمة المعاينة | `backend/fastapi_app/services/web_labs_preparation.py` | Project/Asset/TenantProject، التفويض، قبول المزود، الخزنة، سجل القدرات وWSTG | متطلبات وموانع ومراجع فقط |
| تعريف أول مختبر | `backend/resources/web-labs/bac-orders-v1.json` | fixture الصلاحيات الموجود تحت `e2e/fixtures/bac-target` | تعريف مثبت وبصمة مصدر؛ ليس إثبات نسخة هدف حي |
| تسجيل المسار | `backend/fastapi_app/main.py` | التطبيق الحالي | إتاحة المسار عند دمج الإصدار ونشره |
| الاختبارات | `backend/fastapi_app/services/test_web_labs_preparation.py` | PostgreSQL ومزود اختبار البوابة الحالي | إثبات العزل وعدم الكتابة/الشبكة/dispatch وصحة العقد |
| CI | `.github/workflows/burp-mcp-gateway-reality.yml` | وظيفة اختبار Burp الحالية | تشغيل اختبارات المعاينة بجانب اختبارات البوابة وحفظ JUnit |

المسارات `backend/...` في الجدول نسبية إلى `aegis-platform/`.

## المدخل

| الحقل | القيد والمعنى |
|---|---|
| `project_id` | UUID لمشروع حالي يملكه المستخدم أو ينتمي إليه |
| `asset_id` | UUID لأصل نشط داخل المشروع نفسه؛ لا يقبل عنوان هدف من العميل |
| `lab_definition_id` | التعريف الأول `bac-orders-v1`؛ لا يقبل مسار ملف أو سكربت |
| `credential_refs` | حتى ثلاثة UUID مختلفة؛ بيانات مرجعية فقط، بلا token أو cookie خام |
| `depth` | `quick / standard / deep / comprehensive`؛ الافتراضي standard، ولا يبدأ تنفيذًا |

كل حقل آخر مرفوض بـ422، ومنها `target / command / headers / secret / authorization_id / provider_endpoint`. أخطاء التحقق تعيد اسم الحقل ونوع الخطأ ورسالة عربية، دون إرجاع قيم المدخلات.

مراجع الهويات في P1 تخص هوية الهدف، وليست سر اتصال المزود. نحتاج مرجعين مختلفين، نوع TOKEN أو GENERIC، بهويتي `alice` و`bob` ضمن `scope.browser_identity_ref` وبعنوان `scope.browser_origin` مطابق لأصل الهدف. هذا فحص metadata فقط، ولا يحكم بصحة المحتوى أو انتهاء جلسة الدخول؛ التحقق من المادة الفعلية يؤجل إلى العامل القائم عند التنفيذ.

## آلية الفحص والشرح

| الخطوة | الإجراء الفعلي | سبب الفحص | تفسير الخرج والخطوة التالية |
|---|---|---|---|
| الوصول | قراءة المستخدم النشط والمشروع والأصل | منع خلط المشاريع | غير المتاح يعيد404 بالرسالة نفسها سواء غاب المرجع أو لم يجز الوصول إليه |
| المؤسسة | فحص TenantProject والمؤسسة النشطة والعضوية القائمة | مطابقة حدود بوابة Burp الحالية | عند الغياب لا تعرض بيانات مزود أو مراجع أسرار؛ يصلح الربط من الإعدادات الحالية |
| العنوان | قراءة عنوان الأصل وفحص HTTP(S) وصيغة URL محليًا | منع عنوان تنفيذ من العميل | لا DNS ولا طلب للهدف؛ خطأ الصيغة يشرح المطلوب من إعداد الأصل |
| التفويض | استعمال current_asset_authorization وأحدث قرار | منع استخدام قرار أقدم بعد إلغائه أو انتهاء صلاحيته | يميز missing/revoked/expired/binding_mismatch/projection_disabled بالعربية؛ المراجعة عبر مسار التفويض الحالي |
| المزود | أحدث قرار لكل اسم مزود، والسياسة والبصمات وربط الأدوات وصيغة endpoint | منع تجاهل أحدث قرار أو بيان أدوات غير مقبول | missing/ambiguous/inadmissible/invalid_tool_mapping/invalid_endpoint؛ لا اتصال بالمزود، ولا اختيار تلقائي عند التعدد |
| الهويات | SELECT لحقول metadata فقط داخل المشروع | ربط هويتين بالهدف دون فك الأسرار | يشرح المرجع الملغى أو غير المتاح أو النوع/النطاق المخالف؛ لا سجل استخدام أو last_used update |
| العمليات | مقارنة متطلب المختبر بعمليات البوابة المقبولة | منع اعتبار أي scanner أداة حل طلبات | `burp.http_request` اسم متطلب مقترح؛ غير مدعوم حاليًا، وتحققه وتوافقه من عمل P2 |
| القدرة | قراءة السجل الحالي | الحفاظ على canonical execution | `web.burp-labs` اسم قدرة مقترح وغير مسجل في P1؛ لا dispatcher بديل ولا fallback إلى Nuclei |
| النسخة والتشغيل | إعلان not_verified/not_checked | عدم اختلاق اختبار حي | تحتاج بصمة هدف حي واتصال وعامل وجلسات وتوافق أدوات في المراحل التالية |

حقول كل requirement: `id, state, observed_state, message_ar, suggested_action_ar`.
حقول كل blocker: `code, requirement_ref, observed_state, message_ar, suggested_action_ar`.

## كيف نفهم النتيجة

- `preview_only=true`: هذه معاينة، لا محاولة حل.
- `metadata_ready`: اكتمال بيانات المؤسسة والعنوان والتفويض والمزود ومراجع الهويات في السجلات المقروءة.
- `execution_ready`: لا يصبح true مع وجود أي مانع. في P1 تبقى موانع اتصال العامل وربط النسخة الحية غير متحققة، حتى لو اكتملت metadata.
- `supported_operations`: العمليات المشتركة بين بيان المزود المقبول وقائمة بوابة Burp الحالية، وليست نتيجة استدعاء tools/list أو تجربة فعلية.
- `fixture_revision`: SHA256 لمصدر fixture المثبت؛ لا يثبت أن أي URL مسجل يشغل هذا المصدر.
- `authorization_ref / decision_ref / credential_ref`: مراجع السياق الحالي، لا tokens قابلة للتنفيذ ولا تفويضات جديدة.

HTTP200 يعني أن المعاينة نجحت. لا يعني أن المختبر جاهز أو أنه حُل. الحكم الحقيقي لاحقًا يحتاج مقارنة الموارد والمالك والمستأجر والضابط السلبي على النسخة المثبتة.

## حدود هذه المرحلة

لم تُسحب لابات Academy ولم يُنسخ محتواها إلى مخبر محلي. لم يُثبت اتصال Burp الحقيقي أو إرسال HTTP عبره أو نجاح اللاب. لم تضف واجهة frontend أو جداول أو migrations أو نظام صلاحيات أو queue جديدًا. خدمة المعاينة لا تستدعي Launcher prepare، لأنه قد ينشئ الأصل أو يغيّر التفويض. إنشاء الأصل وإعداد المزود والهويات عند الحاجة يتم بالمسارات القائمة.

## دليل القبول والاستئناف

تغطي الاختبارات العزل، العضوية، أحدث تفويض، المراجع غير المتاحة/الملغاة، نطاق الهوية، أحدث قرار مزود، تعدد المزودين، ربط أدوات مخالف، endpoint مخالف، رفض المدخلات، التسجيل في OpenAPI، وبصمة fixture. حارس SQL يرفض DML داخل الخدمة وداخل خيط API، وحراس فك السر والشبكة وCelery يمنعون أي أثر من المعاينة.

نتائج التشغيل المثبتة وروابط commit وPR وCI تسجل في تقرير المرحلة؛ لا يجوز نسب اختبار المزود التجريبي إلى Burp الحقيقي. عند إرسال «تابع» تبدأ P2 بفحص حالة main وPR، ثم تنفيذ اتصال المزود واختبار توافقه ودمجه مع مسار التنفيذ الحالي.
